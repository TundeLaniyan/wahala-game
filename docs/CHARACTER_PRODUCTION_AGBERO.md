# Stage 4 — Agbero / Park Enforcer: first dedicated 3D character

Visual-quality approval milestone. **Not deployed.** Branch based on production `514be88`; nothing in `src/sim`, `src/ai`,
`src/input` or the combat / collision / campaign data was touched (render-only change).

**What this is, plainly:** a genuine skinned, rigged, animated, mobile-budget 3D character (not a flat image and not a
re-tinted hero). It reads as the right *costume and role* at the gameplay camera and animates every required state. It is
**not** at the visual fidelity of the Gemini concept sheet: the anatomy is stylised "mannequin" geometry with vertex colours,
no baked texture detail, a small simple face. See "Known differences" and "Do we need external tools or an artist".

## 1. What was inspected (Stage 1)

| Question | Finding |
| --- | --- |
| Repository state | `main` holds only the starter docs. Production code and `514be88` live on `claude/wahala-campaign-guidance-expansion-v1`; the work is branched from `514be88` in an isolated worktree. |
| Existing characters | `char_*.glb` (3 heroes + `char_areaBoss`), generated by deterministic Python (`tools/assets/`, numpy/scipy/Pillow, **no Blender**): lofted body, cloth shells, vertex colours, one 22-bone skeleton, procedural clips. |
| Enemy look today | Campaign enemies are the hero rigs (or the Area Boss rig) recoloured with procedural kit pieces (`render/assets/enemyKit.ts`, `assets/enemyLooks.ts`, decision SV4). Explicitly marked TEMPORARY. |
| Loading | `render/assets/library.ts` globs every `src/assets/models/**.glb` and preloads them all; a missing/failed file is just not in the library, every consumer has a fallback. |
| Animation | `RiggedCharacter` (`AnimationMixer`, named clips, cross-fades, `playOnceOver` stretches a one-shot over the sim's wind-up). Clip choice derives from sim state/events in `PlayerViews.ts` only. Enemy wind-ups are 60 / 48 / 38 ticks, recovery root 72 / 60 / 48 ticks (config, unchanged). |
| Collision / scale | Collision is the sim's tile grid; models are drawn at 1.86 tiles tall and never read by the sim. |
| Tools available | No Blender (`bpy` missing), no external modelling or generation service (and none may be bought). Python + numpy/scipy, three.js, Chromium. |

A static turnaround sheet cannot be converted to a faithful 3D character automatically; the model was authored by hand-written
generator code against the sheet's costume, proportions and poses.

## 2. Pipeline (Stage 2)

Recommended and implemented: **extend the existing deterministic generator pipeline** (same skeleton, exporter, viewer, library).

```
tools/assets/enemies.py        Agbero body + outfit (loft/cloth/hard-surface kit, vertex-coloured)   -> spec
tools/assets/enemy_clips.py    Agbero clips on the shared 22-bone rig
tools/assets/build_enemies.py  exports src/assets/models/char_agbero.glb  (via build_characters.build)
tools/assets/glb_report.py     static GLB statistics (size, tris, materials, animation memory)
tools/viewer/pose-sheet.mjs    clip-pose contact sheets under the game lighting
scripts/agbero-shots.mjs       real-game screenshots: new vs legacy, quality, viewport, poses
```

```bash
pip install numpy scipy pillow
python3 tools/assets/build_enemies.py agbero     # -> src/assets/models/char_agbero.glb (deterministic)
python3 tools/assets/glb_report.py src/assets/models/char_agbero.glb
```

Same skeleton as the hero cast (bone names are tested), so the rigging, skin weighting, `head`-bone rule, x-ray silhouettes and
rim light all apply unchanged. `build_characters.build` gained optional `spec` / `clips` / `head_scale` parameters; the hero
builds are unchanged (note: re-running the hero builders in this environment's numpy/scipy versions produces byte-different but
equivalent files, so no existing GLB was regenerated or committed).

## 3. The model (Stage 3)

* `char_agbero.glb`, glTF binary, Y-up, front +Z; rest-pose bounding height 1.99 m including the enlarged head (Area Boss 1.92 m), drawn at the game's usual scale (the look scale stays 1.0).
* Rugged, heavier build than the heroes (wide chest and shoulders, thick neck, forearms), short fade, heavy brow, square jaw,
  stubble shading: an original fictional face, no likeness of anyone.
* Outfit per the sheet: open olive utility vest (chest pockets with flaps and buttons, lower pockets, front binding, standing
  collar) over a dark graphic tee; orange hazard bandana with knot tails on the **right** upper arm; taped hands; utility fanny
  pack on the left hip; radio, aerial and key ring on the right belt; belt and buckle; faded dark jeans with dirty hems;
  scuffed grey trainers with blue and cream panels.
* Silhouette cues for the 35-45 degree camera: broad vest block, bright orange arm band, pale hand wraps, pack at the hip.

## 4. Animation (Stage 4)

All on the shared skeleton, authored in `enemy_clips.py`. Combat timings and hit detection are **not** touched: the clips are
stretched over the sim's own wind-up by the existing `playOnceOver`; nothing in the sim reads animation.

| Required state | Clip | Trigger (existing event / state; presentation only) |
| --- | --- | --- |
| Idle | `Idle` | default |
| Patrol | `Walk` (upright strut, left hand on belt) | moving while territorial mind is `patrol` / `watch` / `return` |
| Pursuit | `Run` (forward lean, pumping fists, head down) | moving in any other state |
| Wind-up (readable) | `Windup`: stance -> coil (torso wound back, rear fist cocked at the ear, weight on rear leg) -> held tension with a visible tremble -> blow in the last 12 % | `attackStarted`, stretched over `resolveTick - tick` |
| Punch execution | last frames of `Windup` + `Strike` follow-through | `skillUsed` / the end of the wind-up |
| Recovery | second half of `Strike` (hold, pull back to guard, heaving shoulders) | after the blow; the sim keeps the enemy planted for its recovery window |
| Generator awareness | `Alert` (point, head and chest turned) | `enemyCue` `alert` / `investigate`; never cuts a wind-up or flinch (`playCue`) |
| Stagger | `Stumble` (existing, shared) | `campaignHit` damaged, whiffed blow, knockdown, hazards |
| Blast / vehicle defeat | `DieBlast` / `DieVehicle` (existing, shared) | the existing death branch |

`RiggedCharacter` maps the generic `Push` request to `Windup` (when stretched) or `Strike` (otherwise) **only when the model has a
`Windup` clip**, so hero and other-enemy behaviour is identical to before.

## 5. Game integration (Stage 5)

* `EnemyLook.model: 'agbero'` (only the Agbero) -> `PlayerViews.create` uses `char_agbero` when it is loaded; the old rig + kit
  path is used when it is not (**safe fallback**), and `?legacyEnemies` forces the old look (art comparison, safe way back).
  This is the controlled development switch: no other variant, boss or hero changes.
* Preserved: AI, generator-first combat, movement and collision, telegraphs (ring, clock, awareness marks), damage and health,
  campaign progression, UI, adaptive graphics (the model has 4 materials, no texture, nothing quality-dependent), loading
  (the GLB joins the existing preload list like every other model).
* Tests: `tests/render/agbero-model.test.ts` (skeleton identical to the heroes, required clips, budgets, only the Agbero has a
  dedicated model, `?legacyEnemies`, the not-loaded fallback, wind-up / strike aliasing, cues never cut a one-shot). Full unit
  suite: 291 files, 4560 passed, 7 skipped (the new file ran separately afterwards: 18 passed with `enemy-looks`).

Existing budget doc says characters <= 9k triangles; the shipped cast already exceeds it (14-17k) and the Agbero is inside the
cast's range, with one fewer draw-relevant material than the Area Boss. Reducing it further (about 9-10k) is feasible by
lowering cloth tessellation and hair/eye detail, at some silhouette cost. `src/assets/models` grows from 19 MB to about 19.9 MB
(the document's 15 MB target was already exceeded before this change).

In game (production build, `scripts/campaign-perf.mjs` with `PERF_QUERY`, mission `oshodi.approach`, two Agberos present,
**software WebGL (SwiftShader), 740x360, 5-13 frames per run: relative numbers only, never phone performance**):

| quality | look | draw calls | triangles | frame mean ms |
| --- | --- | --- | --- | --- |
| low | legacy kit | 155 | 480,665 | 499 |
| low | **new** | 155 | 472,080 | 523 |
| high | legacy kit | 414 | 1,422,838 | 1,192 |
| high | **new** | 410 | 1,409,790 | 1,209 |

`oshodi.railEdge` showed legacy 537 / 1,216 ms and new 496 / 1,207 ms (low / high), i.e. differences in both directions: **no
observable frame-time regression, but the sampling is too small and the renderer too slow to resolve a few percent**. The scene
cost per Agbero is lower than the legacy kit look (both measured missions hold exactly two Agberos: about 4,300 fewer triangles each at low and 6,500 at high, equal draw calls). No real-phone test was
done; do not read these as phone results. Initial load bytes are identical in both modes (the GLB is bundled either way); the
asset's own added load cost is 852 KB raw / 337 KB gzip.

## 8. Known differences from the Gemini concept

* **Anatomy and surface.** The concept is a photoreal-style sculpt with muscle definition, cloth thickness, stitching, worn
  leather and denim texture. This model is lofted tubes with vertex colours (as the whole current cast), so forms are smooth
  and simplified, limbs thinner than the concept, no muscle definition, no skin or fabric pores, no normal maps.
* **Face.** Small and simple (eyes, brow, ears, nose and jaw from the shared head generator); the four expressions are not
  modelled. Under the gameplay camera the face is a few pixels; it does not carry the concept's identity.
* **Costume detail.** All the concept's pieces are present, but the tee print is a soft blob, the radio, keys and pocket flaps are
  tiny boxes, the trainers are generic. Vest silhouette is a closed tube with a cut front, not a hanging garment.
* **Proportions.** Heads use the cast's 1.3x enlargement then the game's runtime 0.82 factor (about 1.07 net), hands are mitt-like
  under the wraps, hands and fingers are not articulated (no finger bones in the shared rig).
* **Poses.** The concept's seated defeat against tyres is not built; the existing blast tumble is used. Pose silhouettes of the
  other five action poses are matched in intent, not frame by frame.
* **Colour/lighting.** The sheet is rendered with studio lighting; in game the model is shaded by the game lighting and grit.

## 9. Repeatability for the other 17 characters

* **The workflow is repeatable** for a *consistent stylised look*: a new `enemies.py` builder + clip set per character, same
  skeleton/exporter/tests/screenshot tools; roughly the Agbero effort for similarly costumed human enemies (Area Boy, Bottle
  Thrower, Market Enforcer, Heavy, Marshals, Guards; the Ring Lieutenant too). Variant differences (bulk, headwear, props) are
  mostly parameters. The dedicated-model switch (`EnemyLook.model`) and the per-variant fallback generalise directly.
* It will **not** reach the concept sheets' fidelity for the 7 bosses and 3 heroes with distinctive faces, hair (locs, twists),
  agbada / jacket tailoring or props, without new capability (below).

## 10. External tools or an artist?

Yes, for the approved quality. Honest recommendation:

1. **To match the Gemini sheets**, a 3D character artist using Blender (or ZBrush + Blender): sculpt/retopo a ~10-15k triangle
   body and head per character, bake PBR textures (a 512-1024 px atlas), and skin to the **existing 22-bone skeleton** so all clips
   and the game integration here are reused as is. This costs money/people: not started without your authorisation.
2. **Cheaper intermediate**: keep this pipeline but add UVs plus a small hand-painted texture atlas (tee print, vest wear, denim
   fade, face), more face/hand geometry and proper hair cards; improves read without an artist, still stylised.
3. An AI image-to-3D service could produce fast, fairly faithful meshes, but typically needs retopology, rigging and clean-up
   to meet the mobile budget and skeleton, and has licensing/consistency questions: needs your decision and a trial on one
   character before adopting. None was used here.
