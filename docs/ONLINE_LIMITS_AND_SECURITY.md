# City Rumble online: capacity limits, abuse protection and security (branch `claude/wahala-fu2-server`, decisions FU2S-C1 to FU2S-C5)

Online stays **dormant and development-only**. Nothing here enables it in the public build, hosts anything, opens a port beyond localhost / LAN development, or adds an account, a ranking, a reward, a payment or voice. ## 2. QUICK PLAY: a genuine Free-for-All / Team Rumble choice (decision FU2S-C1)

- The entry screen has a mode picker (Free-for-All / Team Rumble) above the QUICK PLAY button; the button and the note name the mode. The choice is held in the page's memory only (nothing new is stored).
- The client sends `joinOrCreate('rumble', { name, characterId, gid, mode })`. The server registers the room type with `filterBy(['mode'])`: the matchmaker only offers a public room opened for the **same** mode. Free-for-All is the Deathmatch ruleset, Team Rumble the Team ruleset (`quickModeGame`). An unknown `mode` is refused (`unknown mode`); a missing one (an older client) means Free-for-All. Nobody is ever moved to the other mode: a Team request with no Team room waiting opens a Team room. The room also refuses a joiner who names another mode (backstop).
- **Teams are balanced by the server** (the simulation's `assignTeams`: 16 v 16 over the 32 seats, humans spread because seats alternate sides, bots fill; unchanged from PIS2 and proved for 1, 2, 5, 17 and 32 humans by `server/test/teams.test.ts`).
- **Friendly fire follows the offline rule: OFF, and nobody can change it in a public room.**
- **A public room's settings belong to the server.** At creation only the mode comes from the player; stage (`rumbleOshodi`), length (300 s), bot level (`standard`) and friendly fire (off) are the server defaults, whatever the client sends. After creation `settings` from any member, **host included**, is refused with a `public_room` notice, before or after others joined, and the room screen shows the settings read-only with the reason. A **private** room keeps full host control (stage, mode, length, bots, friendly fire in Team). Decision: a public host may change **nothing**; a player who wants to choose creates a private room.
- **Public rooms are not joinable by code**: quick play is their only door (otherwise a code shared from the lobby view would bypass the mode choice); a join by code to a public room gets the uniform "room not available" answer.
- The 30 s public wait, bot fill, lock at the start and "no new humans after start" are unchanged (PIS1, PIS4).
- Tests: `server/test/capacity.test.ts` (C1 block: modes never mix, same-mode players share, defaults, client settings ignored, host refused with `public_room`, private room unchanged, public not joinable by code), `tests/ui/rumble-online-screens.test.ts`, `tests/app/rumble-online-flow.test.ts`, `tests/ui/rumble-online-models.test.ts`, and the browser lobby check `e2e/rumble-online.spec.ts` (local, gated by the online build).

## 3. Server-authoritative limits (decision FU2S-C3)

All in `server/src/core/guard.ts` (pure, injected clock) and `limits.ts`; the Colyseus glue is `app.ts` (every matchmaking request) and `RumbleRoom.ts` (room creation, match start, connections). Every number is an environment variable (`loadLimits`), has the default below and a test (`limits.test.ts`, `guard.test.ts`, `capacity.test.ts`); a malformed value falls back to the default, so a typo never hard-fails honest play.

| What | Default | Env | Why this number |
| --- | --- | --- | --- |
| Rooms of any phase on the process | 120 | `RUMBLE_MAX_ROOMS` | an idle lobby costs ~1 MB; 120 lobbies are far below the memory of the smallest host |
| Rooms counting down or playing at once | 8 | `RUMBLE_MAX_PLAYING_ROOMS` | each runs a 60 Hz simulation |
| Estimated CPU of all running matches (percent of ONE core) | 75 | `RUMBLE_CPU_BUDGET` | 3 rooms of 1 human + 31 bots measured about 72 % (section 4); leaves headroom on the single event loop |
| Event-loop p99 above which no further match starts | 150 ms (only while a match is running) | `RUMBLE_START_LOOP_LAG_MS` | the soak showed p99 25 ms with 3 bot rooms; above 150 ms players already feel it |
| A room waits for a match slot at most | 120 s, then closed with `server_busy` | `RUMBLE_START_WAIT_SEC` | a clear failure beats an endless wait |
| Open human connections | 600 | `RUMBLE_MAX_CONNECTIONS` | measured to 256 clients on one process; 600 is the ceiling before memory / egress matter |
| Rooms one guest session owns at once | 3 | `RUMBLE_MAX_ROOMS_PER_GUEST` | one match plus a rematch lobby plus a spare |
| Rooms one address (IPv6: a /64) owns at once | 40 | `RUMBLE_MAX_ROOMS_PER_IP` | a backstop only: a carrier address serves many players |
| Room creations per guest | burst 4, 6 / min | `RUMBLE_GUEST_CREATE` (`burst/perMin`) | an honest player creates one room per match |
| Joins and quick plays per guest | burst 20, 30 / min | `RUMBLE_GUEST_JOIN` | |
| FAILED joins by code / reconnect tokens per guest | burst 6, 6 / min | `RUMBLE_GUEST_JOIN_FAIL` | a few typos are honest; code guessing is not |
| Per-address ceilings: creations, joins, failed joins, WebSocket upgrades | 60 + 120 / min, 200 + 600 / min, 60 + 60 / min, 300 + 900 / min | `RUMBLE_IP_CREATE`, `RUMBLE_IP_JOIN`, `RUMBLE_IP_JOIN_FAIL`, `RUMBLE_IP_UPGRADE` | generous on purpose (carrier-grade NAT) |
| A lobby / results screen nobody touched | closed after 900 s (pings and game inputs do not count as use) | `RUMBLE_LOBBY_IDLE_SEC` | frees abandoned rooms; 15 minutes is longer than any wait for friends |
| A client whose unsent output exceeds | 2 048 KiB: cut off, may not reconnect | `RUMBLE_MAX_BUFFERED_KIB` | a client that does not read would pile frames up in server memory |
| Retry hint on `server_busy` | 20 s, +0..25 % jitter | `RUMBLE_BUSY_RETRY_SEC` | a refused crowd must not come back together |

**Who is limited.** The primary key is the **temporary guest session id**: the page makes 128 random bits (`crypto.getRandomValues`), keeps them in memory only (a reload is a new guest; nothing is stored, PIS6) and sends them as `gid` with every matchmaking request. A request with no `gid` (a script, an older client) shares its **address's** bucket, so omitting the id never buys a fresh bucket. Per-address ceilings are a backstop with generous numbers. Honest limit of this design: a hostile script can invent guest ids, so the per-guest buckets protect honest players from each other and from a buggy client, **not** from a determined attacker; against that the **global** caps (rooms, playing rooms, CPU budget, connections) and the per-address ceilings are the protection, and they are enforced where the room is built, so no path bypasses them.

**Every path goes through the limits.** All HTTP matchmaking (`create`, `joinOrCreate`, `joinById`, and in development `reconnect`) goes through `guardedInvoke`; `join` (join without creating) is not exposed; the room's own `onCreate` re-checks the global caps (so `matchMaker.create` from code and a quick play that races another one cannot exceed them); WebSocket upgrades are counted per address in `beforeUpgrade`; joins count against the connection cap in `onJoin`. **No WebSocket message can create a room or start a match outside the room it is in**; the only messages are input, ping, resync, ready, start / rematch / settings (host, private rooms) and each is rate-checked and validated (flood: more than 600 messages in 5 s, or more than 20 invalid in 10 s, closes the client with 4400; frames over 4 KB are closed by the transport).

**The wire contract of a refusal.** `server_busy` (HTTP 503, WebSocket close 4401 for a room that waited too long), `rate_limited` (HTTP 429) and `room_unavailable` (HTTP 404) travel in the error message as `code;retry=<seconds>;<plain words>` (`encodeBusy` / `parseBusy` in `src/net/protocol.ts`, shared by server and client). The client maps them to `server-busy`, `rate-limited` and `room-unavailable` and the entry screen says, in plain words: "The servers are busy ... Nothing is wrong on your side: try again in about 25 seconds." / "Slow down a little ... Wait in about 8 seconds and try again." / "That room is not open: the code may be wrong, the room may be full or closed, or its match may already have started." Rooms waiting for a slot send a `server_busy` notice every 10 s and the lobby view carries `waitingForSlot`, which the room screen words as "The servers are busy: your match starts as soon as a slot is free."

**Fairness.** Refusals are equal for everyone (no priority by address); a crowd refused together gets jittered retry times; honest play is never limited by the per-address numbers on their own; a room that already runs is never touched; rooms waiting to start are served strictly in arrival order (a small room cannot overtake an older big one).

**Cleanup and backpressure.** Idle lobbies expire; created-but-unused rooms are disposed by the seat reservation; a closed server disposes every room, frees the guard and leaves no timer of its own (test with every JS timer recorded); per-client message rate and size limits existed and are kept; the outbound-buffer limit above is new; the `/metrics` `limits` block exposes the guard.

## 4. The CPU budget, from measurements

`ROOM_BASE_COST = 10` (percent of one core for a room of 32 humans: simulation, replication, sockets, measured 9.3 to 10.6 %) and `BOT_COST = 0.45` per server bot (one bot brain, measured 0.43 to 0.46 %), so a room of 1 human + 31 bots costs `10 + 31 * 0.45 = 24 %`. The budget is the sum of the running rooms' costs; a new match starts only while `costInUse + cost <= RUMBLE_CPU_BUDGET` (75), the playing-room cap has room, and the event loop's recent p99 is under 150 ms. An empty server always runs one room, whatever the budget (a tiny budget never deadlocks a lone player). Consequences with the defaults: 3 rooms of 1 human + 31 bots (3 x 24 = 72 %), or 6 rooms of 32 humans (6 x 10 = 60 %), or a mix; a 4th bot room waits.

Evidence the model rests on (all from this server, one process, 4 shared vCPUs):

| Measurement | Source | Result |
| --- | --- | --- |
| 32 humans, clean network | `docs/CITY_RUMBLE_ONLINE.md` 7.2 (`npm run load`) | 9.3 to 10.6 % of a core, 0 dropped ticks |
| 1 room of 1 human + 31 bots | 7.5 and the Ops audit (two independent runs) | about 24 % |
| 3 such rooms | 7.5, the PIS8 soak, the Ops audits | about 72 to 74 %, event-loop p99 25 ms, 79 dropped ticks in one sample |
| 4 / 6 such rooms | 7.5, Ops probe | 94 % with 47 dropped ticks / saturated, p99 150 ms, 370 dropped ticks |
| **6 rooms started at once, no budget (probe "before", this branch's measurement, machine shared with other workers)** | `abuse-probe-before.json` | **98 % median CPU (max 102), event-loop p99 181 ms median / 265 max, 1 320 dropped ticks in 20 s** |
| **The same 6 rooms with the budget (probe "after")** | `abuse-probe-after.json` | **3 playing (cost 71.9 of 75), 3 waiting in their countdown with the "servers are busy" notice; 80 dropped ticks, p99 87 ms median (the box was loaded by another worker's browsers, load average 7 to 9 on 4 CPUs)** |

`docs/measurements/rumble-online/capacity-model.json` holds the constants and the points they were fitted to. The model is a fit to two ends (0 bots: 10 %, 31 bots: 24 %); it was NOT checked at other bot counts, and a different CPU needs a new fit (re-run `npm run load` / `npm run soak` on the real host and set `RUMBLE_CPU_BUDGET`). The 30-minute soak (`docs/CITY_RUMBLE_ONLINE.md` section 7.8) ran 3 room slots under a machine that was loaded by other work (load average 6 to 10 on 4 CPUs): server CPU mean 48 %, max 88 %, 0.45 % of ticks dropped; it is not a capacity measurement and the budget was not tuned on it.

## 6. Tokens, reconnection and page reloads

- **Strength.** Colyseus generates the session id and the reconnection token with `nanoid(9)` (64 symbols, 54 bits) inside `Room` (`generateId`, not injectable: the function is bound at import time in `@colyseus/core`). Raising it to 128 bits means forking the library, which this work does not do. The 54-bit token is therefore **documented, not raised**, and made harmless by what surrounds it: (1) the only reconnection door in production is the WebSocket, which needs the room id AND the session id AND the token (two independent 54-bit secrets, 108 bits, the session id never sent to anyone else); (2) the HTTP `reconnect` method (one token) is **not exposed in production** (`exposedMethods`), only in development for tests and the load harness; (3) a token exists only while its seat is held (30 s) and is single-use and rotated on every connection; (4) guesses against it are rate-limited per guest and per address; (5) the upgrade itself is rate-limited per address. At the generous per-address ceiling a guesser makes about 60 attempts a minute: 108 bits is out of reach by any margin; even the single 54-bit token over the development-only HTTP door would take about 5 x 10^8 years at that ceiling (2^54 / 60 per minute), against a token that lives 30 s.
- **Rotation.** Every connection (first join and every reconnect) gets a fresh token; the old one is dead the moment the new socket is accepted (`identity.test.ts`: the owner's token works once, the old one is refused).
- **A page reload.** The SDK keeps the token in memory only, our client never stores or reads it, and the guest session id is also in memory only (PIS6, `tests/online/identity-and-wording.test.ts`). A reload therefore loses both: the new page cannot reclaim the old seat, and cannot hold it either: the dropped seat is held by the SERVER for one window of `RUMBLE_RECONNECT_SECONDS` (30 s) counted from the drop, then it is a bot's for good, whatever the page does. No code path extends or restarts a window: it is one `allowReconnection(client, 30)` per drop. Proven in real time: `server/test/room.expiry.realtime.test.ts` (section 9).
- **Short-lived storage.** Nothing was added to `sessionStorage` / `localStorage` (the Ops audit's SRV-8 suggestion would make an iOS background-kill survivable but lets page script read the token; the decision is left as it was: memory only). The cost, stated plainly: a phone whose page is killed by the OS (not merely frozen) cannot return to its fighter.

## 9. Online reliability: what the two-browser e2e failures were (decision FU2S-C5)

`npm run test:online-e2e` (two real Chromium browsers, one real server, a 32-fighter match with a 30 s network loss of one player) passed on a quiet machine and failed intermittently under CPU pressure: once both browsers dropped for about 8 s at match start with a host chip RTT of 8 342 ms, and the Ops branch saw two failures with **different** symptoms (the touch pad not found; the reconnect banner still shown 120 s after the network came back). The cause was investigated, not retried around. Instrumentation added: the runner samples the server's own `/metrics` once a second (event-loop delay, CPU, dropped ticks, timer lateness, machine load) and prints a verdict; the server logs every drop, return and permanent leave **with its close code**; each page records its WebSocket opens / closes with code, reason and cleanliness, its main-thread long tasks and its animation-frame gaps (`e2e/onlineDiag.ts`); the Colyseus reconnection log lines are kept in the timeline.

**Evidence (a deliberately contended run: the machine's load average reached 14.8 on 4 CPUs because other workers' browsers ran at the same time).**

**The "stick-zone bounding box is null" failure (the Ops branch's run 1, and one of ours on a later run) is a third, smaller cause: the test, not the game.** The touch pad is on screen only while the fighter is alive. A page starved at match start leaves its fighter standing through the 3 s grace period, a rival's blast can down it before the page draws a frame, and the page snapshot at the failure shows `DOWN` / `Back in 2`, 2:57 on the clock, the connection chip `ONLINE 158 ms`, both sockets reconnected: the connection was fine and the spec read a bounding box that was `null`. The spec now waits for the pad to be visible (the respawn) before using it. Nothing about reconnection was relaxed.

**The three leads, answered.** (a) After both sockets closed together at match start the guest page was in a long task of tens of seconds: starved, not broken. (b) The client reconnect loop is not at fault: `maxRetries` 30 with 0.2 to 2 s backoff covers about 55 s, the token is only consumed by the server when a socket is accepted, and the banner stayed because the server answered 4003 for a seat it had already given away. (c) Server ping liveness behaved as designed; the server's own event loop never stalled for more than 0.8 s.

**The real defect (decision FU2S-9).** Colyseus' `allowReconnection` refuses a connection that "never fully joined": a client counts as joined only after its page ran the join acknowledgement. A reconnected browser whose main thread is busy (or a mobile link that flaps right after a reconnect) can be dropped again before that acknowledgement; `onDrop` then got an immediate rejection, Colyseus called `onLeave`, and the room replaced the seat with a bot FOR GOOD although the 30 s window had just begun: a refused (4003) page, a permanently lost fighter. The room now clears the "never joined" flag before holding the seat (the player was admitted: their lobby entry and fighter exist), logs `could not be held` if Colyseus still refuses, and counts `dropsBeforeAck` in `/metrics`. Regression test `server/test/room.reconnect-flap.test.ts` (a raw socket takes the seat back and never acknowledges, the link drops again: the seat must stay held, a bot plays it, and the player can still return with the new token); it fails without the fix.

**Making the check resource-stable without hiding reconnect failures.** The check was overcommitting the machine: two software-rendering browsers and the server on 4 CPUs. Now: the runner pins the server to CPU 0 and everything the browsers spawn to the other CPUs at a lower priority (`ONLINE_E2E_PIN=1`); the `light` profile (`ONLINE_E2E_PROFILE=light`) renders both pages at phone size at the lowest quality; the runner prints a server verdict and with `ONLINE_E2E_ASSERT_SERVER=1` (the CI job) fails when the SERVER stalled (loop delay over 0.5 s, more than 2 % of a room's ticks lost, or `/metrics` not answering; it was "any dropped tick" until CI run 330, which failed with 5 of 5 tests passed, a 130 ms worst loop delay and ONE lost tick: decision FU2-CI7), because then the browser result means nothing; nothing is retried (`--retries=0`) and no assertion about the reconnect was relaxed. **Result with the fix, the light profile and the pinning, on the same overloaded machine** (another worker's browsers kept the load average between 10 and 15.5 on 4 CPUs the whole time): `npm run test:online-e2e` with `ONLINE_E2E_PROFILE=light ONLINE_E2E_PIN=1`: **4 of 4 tests passed (10.3 min)**, including the 32-fighter two-browser match with the guest's 30 s network loss, the touch pad and identical results on both screens. The pages were still starved (host: 64 long tasks, the worst 43 s; guest: 72, the worst 43 s) and both dropped once at match start, the guest also during its own 30 s offline step (8 failed reconnect attempts against a dead network, then back); every drop returned to the same seat and no seat was lost (the server log has no `could not be held`). The runner still printed `SERVER STALLED` (event-loop delay up to 1.16 s, 1 857 dropped ticks, 6 `/metrics` calls unanswered in 617 samples): the machine was oversubscribed, which is exactly what the verdict is for; in the CI job (`ONLINE_E2E_ASSERT_SERVER=1`) that would fail the job instead of letting a browser result stand on a starved server. **Not demonstrated:** a run on a machine with nothing else on it (none was available: the box was shared with other workers for the whole session); Later runs of the final code on the same shared machine (load average 8 to 11): the new quick-play lobby check alone passed (48 s, server healthy: loop delay max 87 ms, 0 dropped ticks); one full run failed at the touch pad (the third cause above, fixed in the spec); the next **full run passed 5 of 5 (9.7 min)**.

**The 30 s window with the real clock (decision FU2S-11).** `server/test/room.expiry.realtime.test.ts` uses the production window (30 s) and grace (5 s) with no fake timers: two players are dropped at the same instant, one returns at about 20 s to the same fighter and the same keyframe path, the other stays away and its late return, made about 31.5 s after the server noticed the drop, is refused on both doors (the matchmaking HTTP reconnect answers `room_unavailable`: "the time to come back has ended"; the raw WebSocket is closed with an error and never welcomed); the seat is then a bot's for good and the match's books show `autopilotTicks` for it. It takes about 45 s of wall clock.
